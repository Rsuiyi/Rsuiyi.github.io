Agent Memory 论文调研：构建端 / 查询端算法与省 Token 标注

调研日期：2026-08-05
调研方式：32 篇论文全部经子代理联网核实（Semantic Scholar 元数据 + arXiv/ar5iv 全文 HTML 经服务端抓取），方法细节取自论文正文/附录，非凭记忆。每篇标注信息置信度（高/中/低）。
调研背景与目标（本项目核心痛点）：

  1. 构建/查询 token 失衡：构建（写入）记忆所需的 LLM token 远多于查询（检索）所需的 token。
  2. 精度不高：现有方法 F1/BLEU 普遍 ~0.6，LLM-Judge 普遍 ~0.82。
  3. 多查询提精度但费 token：多条查询可提升精度，但消耗更多 token。
    目标：设计高效的 Agent 记忆与查询算法，在现有 QA 对查询精度提升 20% 的情况下，构建所需 LLM token 减少 50%、检索所需 token 尽量保持不变。

1. 综合结论与横评

1.1 构建端省 token 的六大技术路线

#路线代表系统效果 / 关键点
1写入侧零构建 / 查询时构建（deferred construction）LazyMem、True Memory、GAM、MemCoT把「构建」推迟到查询时刻，写时不压缩。True Memory 摄入零 LLM 调用；LazyMem 写时零压缩。构建端 token 直接归零，远超 -50%。
2一次性联合抽取替代多步 LLM 调用SimpleMem、GRAVITY、Mem-αSimpleMem 单遍完成「门控过滤+共指消解+时间锚定」；GRAVITY 把三种抽取合并为单次 LLM 调用（构建 prompt token -75%）。
3只存增量 + 去重 / 校验AtomMem-USTC、Mem0、SimpleMemAtomMem 只存「残余新信息」$c’_{new}$、冲突才更新；Mem0 用 NOOP 去重；SimpleMem 写时在线合成去冗余。

1.2 查询端省 token / 持平的路线

#路线代表系统效果 / 关键点
1廉价非 LLM 检索链路True Memory、A-Mem、MemoryBankFTS5 词法 + sqlite-vec 稠密 + RRF 融合 + 交叉编码器重排，LLM 仅用于 query expansion 与最终生成；A-Mem 检索环节零 LLM 调用。
2门控按需升级（fast path + 深度回退）D-Mem、MemCoT、LazyMemD-Mem 用 1 次 LLM 质量门控拦截 ~75% 的查询走快速路径，用全量深思 35.8% 的 token 恢复 96.7% 性能；MemCoT judge 早停。
3预算 / 重排 / 紧凑注入Retain-or-Consolidate、Mem0、AMA、GRAVITY注入紧凑结构化 block；Mem0 查询平均 1764 token（vs 全量 26k，>90% 节省）；AMA 相对全量 -80%。
4主动预加载 / 调度 / 分层下探MemOS、HiMemMemOS Next-Scene Prediction 预加载避免冗余注入，token -60.95%；HiMem best-effort「Note 优先、按需下探 Episode」。
5检索结果压成单条行动摘要PlugMem、NEMORI、HeLa-Mem、SimpleMemPlugMem Reasoning 模块 10–26× 上下文缩减；NEMORI 每查询 2745 token（-88%）；HeLa-Mem 1010 token；SimpleMem 531–583 token（-30×）。

1.3 精度提升机制

  1. 结构化表示（图/事实/关联）：$Mem0^g$、A-Mem、HeLa-Mem、AtomMem、Zep —— 语义相似度之外的关联/关系结构是提精度的主来源。
  2. 检索端主动重建 / 多跳检索：MRAgent（LoCoMo 上 LLM-Judge +23.3%）、GAM（深度研究）、MemCoT（记忆驱动 CoT）。
  3. 数据驱动学习替代人工启发式：CMI-Mem（CMI 信息论奖励）、Mem-α（QA 回报 RL）、Mem-T（稠密奖励）、LazyMem（RL 联合奖励）。
  4. 多粒度互补：TriMem（原文+事实+profile）、HiMem（Episode+Note）、AMA（原文+事实+情节）。
  5. 蒸馏选「值得记的」：NEMORI（预测编码，预测误差蒸馏 vs 直接蒸馏 +25%）。

1.5 关键洞察与研究空白

  • 目前没有任何一篇同时达成「构建 -50% + 查询持平 + 精度 +20%」——这是明确的空白点，可做。
  • 构建端最贵的永远是「多步逐 chunk LLM 调用」（A-Mem 每写一条 ≥3 次 LLM 调用、Zep 多步图抽取、HiMem 三段抽取、TriMem 的 TextGrad 优化）。要减构建 token，要么后置构建（LazyMem/True Memory），要么合并成单次/单遍调用（SimpleMem/GRAVITY）。
  • 「查询持平」最容易达成：廉价非 LLM 检索链路（True Memory、A-Mem）+ 门控按需升级（D-Mem）+ 紧凑表示注入（HeLa-Mem、PlugMem）都能让查询 token 远低于全量且不加 LLM 调用。
  • 警惕反向设计：GAM/MemCoT 把构建做轻但把查询做重（深度研究/多轮迭代），会放大「查询贵」的问题——若采用「查询时构建」架构，必须配预算硬帽（LazyMem 的 213 token、MRAgent 的 8 轮×10 工具）。
  • 安全性约束：构建端做摘要/合并会引入原文不存在的「具体性」污染（Remembering More Risking More），压缩记忆需保留溯源指针（TriMem、HeLa-Mem 的证据链接），同时可作为低成本保险丝（检索时监控器）。

2. 逐篇详表

A. 增量「提取-更新」类

Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory

  • Venue/Year: ECAI 2025（arXiv:2504.19413）
  • 作者: Pratik Chhikara et al.
  • 类型: 系统构建（含大规模实证评测，LOCOMO 基准）
  • 核心思想: 增量式「提取 + 更新」两阶段记忆架构：只把对话中最精炼的事实写入知识库，查询时选择性检索紧凑记忆而非原文 chunk；另有图记忆变体 $Mem0^g$（实体为节点、关系为有向带标签边）强化关系推理。
  • 构建端算法 (Write/Build): 增量处理——新消息对 ($m_{t-1}$, $m_t$) 到来时，用 LLM 提取函数 $\varphi$ 从 prompt P = (会话摘要 S + 最近 m=10 条消息 + 新消息对) 中抽取一组显著事实 $\Omega$；摘要由异步模块周期刷新（不阻塞写延迟）。随后对每个候选事实 $\omega_i$：先从向量库检索 top s=10 条语义最相似记忆，把「候选事实 + 检索到的旧记忆」通过函数调用交给 LLM，由 LLM 判定四种操作之一——ADD（无语义等价时新建）、UPDATE（补充既有记忆）、DELETE（矛盾记忆被删）、NOOP（无需改动，跳过）。图变体 $Mem0^g$：Neo4j 中两级 LLM 管线（实体抽取器 + 关系生成器产 ($v_s, r, v_d$) 三元组），新三元组先做实体嵌入相似度找既有节点再建边；冲突检测 + LLM update resolver 判定旧关系是否过时（标记 invalid 而非物理删除，保留时间推理）。token 消耗点：每消息对的提取调用 + 每事实一次的更新判定调用（构建端多次 LLM 调用）。
  • 查询端算法 (Read/Query): 基准 Mem0 为选择性稠密检索——只取最相关紧凑记忆拼入上下文，再生成回答。$Mem0^g$ 双路检索：(1) 实体中心法——识别查询中关键实体，语义相似定位知识图谱节点，扩展入/出边构建子图；(2) 语义三元组法——整条查询编码为稠密向量，与每个三元组的文本编码做细粒度相似度，超阈值按相似度降序返回。随后一次 LLM 生成回答。
  • 省Token标注: 有且量化最充分（集中在查询端）：查询平均只带约 1764 tokens（Mem0）/ 3616（$Mem0^g$），相对全量上下文 ~26000 tokens 节省 >90%；p95 总延迟 1.44s（相对全上下文 ~17s 降约 91-92%），search p50 0.148s 为所有方法最低。构建端亦有节约设计：增量按消息对处理 + NOOP 去重（避免冗余写入）+ 异步摘要不阻塞。相对 OpenAI 自带记忆（LLM-as-a-Judge J 指标）相对提升 26%；图变体比基准高约 2pp（总体 J：Mem0 66.88% vs $Mem0^g$ 68.44%，全上下文 72.90% 但代价是 15× token）。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 最接近目标的模板。构建端用「紧凑事实提取 + NOOP 去重 + 增量逐对处理」把写入控制在 LLM 调用次数与输入窗口（m=10 + 摘要）上；查询端「只检索紧凑事实」实现 >90% 查询 token 节省，远好于「持平」。缺点：构建端每事实一次更新判定调用，仍有压缩空间。
  • 信息置信度: 高

D-Mem: A Dual-Process Memory System for LLM Agents

  • Venue/Year: arXiv:2603.18631（2026-03 预印本）
  • 作者: Zhixing You et al.（Jiachen Yuan, Jason Cai；希伯来大学 + AWS AI）
  • 类型: 系统构建（双过程记忆系统）
  • 核心思想: 模拟人类「系统1快思考/系统2慢思考」：保留轻量向量检索（Mem0*，System 1）处理常规查询，另设「全量深思」（Full Deliberation，System 2）作为高保真回退，用「多维质量门控」（Quality Gating）动态决定何时升级——既规避压缩式记忆的「有损抽象」，又不为每个查询付出全量深思的高成本。
  • 构建端算法 (Write/Build): Mem0 式增量处理（增强为 Mem0）：每来一轮新对话（消息对），LLM 在两类上下文上抽取显著记忆 $\Omega$——(1) 向量库中语义最相似的 top-10 旧记忆，(2) 最近 10 条消息（时间上下文）；随后对每个候选 $\omega_i$ 检索 top-5 相似旧记忆，用严格余弦阈值（>0.8）丢弃低相关项形成背景集 B，再让 LLM 交叉比对 $\Omega$ 与 B 判定矛盾/冗余，执行 ADD / UPDATE / DELETE / NOOP。*token 消耗点：每轮抽取调用 + 每个候选的比对调用（增量小步更新）。本文省 token 核心不在构建端，而在查询端门控路由。
  • 查询端算法 (Read/Query): 查询时 Mem0 检索 top-30 记忆 C，生成初始答案 $A{init} = LLM(q, C)$；可选 Filter 步骤再用 LLM 把 C 裁剪到只留必要记忆（全裁空时回退用原 C 保召回）。随后 Quality Gating 用 LLM 按三维度评分（相关性 Relevance、忠实一致 Faithfulness & Consistency、完整性 Completeness），三维全过 → 直接输出 $A{init}$；任一不过 → 触发 *Full Deliberation：把全部对话历史切成 60 条消息/块，每块用 LLM 以查询为锚抽取相关事实并打 0-10 相关性分（带 4 条滑动窗口保连贯），按分排序、>6 初筛、若剩 >6 条再 LLM 二筛，用过滤后事实替换 top-30 记忆生成最终答案。
  • 省Token标注: 有，量化明确，属「查询端省 token」：LoCoMo（GPT-4o-mini）上 Quality Gating 用 12,681 token 达到 F1 53.5，恢复 Full Deliberation（F1 55.3，35,435 token）96.7% 的性能，只用其 35.8% 的 token、约 1/3 推理延迟；相比 Consensus 策略省 19.5% token。约 75% 的查询留在快速路径（LoCoMo 24.1% 触发回退，RealTalk 24.7%）。手段是「按需升级」的预算控制，而非写端压缩。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 查询端是省 token 主战场——一个廉价门控（约 1 次 LLM 判断）就能拦截 ~75% 不需要深思的查询，做到「查询 token 基本持平甚至更低」。其精度上界（Full Deliberation F1 55.3）也仅比快速路径高 4 个点，说明「把检索做精 + 按需深思」性价比远高于全量处理。但对「构建减 50%」无直接贡献（构建端仍靠 Mem0 式抽取），可作为查询端配套组件。数据与项目痛点吻合：其 LoCoMo F1≈53.5、LLM-judge 76.3。
  • 信息置信度: 高

CMI-Mem: Toward Generalizable Long-Term Memory Management via CMI-Augmented Reinforcement Learning

  • Venue/Year: arXiv:2607.20553（2026-07 预印本；代码 github.com/Wyb0627/CMIMem，模型 CMI-Mem-4B）
  • 作者: Yubo Wang et al.（阿里 + 港科大 + 港理工）
  • 类型: 系统构建（RL 训练轻量记忆管理器）
  • 核心思想: 针对「现有记忆管理器过度依赖 LLM-judged 合成 QA 对、记忆价值被采样查询和下游 reader 绑架」的问题，用条件互信息 CMI 作内在奖励：CMI 衡量新对话相对当前记忆状态贡献了多少信息，不依赖采样查询，与下游 QA 正确率（外在奖励）互补。RL（GRPO）训练一个轻量 4B 记忆管理器。
  • 构建端算法 (Write/Build): 记忆状态分 4 个认知槽位：core（有界用户画像，$L{core}=5000$ 字符，常驻 prompt 不进向量库，超 90% 触发压缩到 3000 字符以下）、episodic（带时间戳事件）、semantic（事实/概念）、procedural（流程）。四个类型专用 agent 共享同一策略 $\pi\theta$，动作空间各异：$core{Append, Replace, Rewrite}$、$epi{Add, Update, Merge, Skip}$、$sem{Add, Update, Skip}$、$pro{Add, Update}$。每个会话每个 agent 观察上下文 + 对应槽位 top-$k$=20 相关条目，输出一个动作 + 候选记忆片段 $m{new}$；产物片段同时作为指向源对话轮次的「检索索引」。写端奖励：CMI 用残差投影估计 $I(C_t; m{new} \mid M^{local})$（Gaussian 整形），按动作类型打分（Add/Merge 取 $\max(0, \hat{r})$，Replace/Update 取净增益 $\Delta\hat{r}$），最终 $rt = \alpha \cdot \tilde{r}{CMI} + (1-\alpha) \cdot r_{QA}$（α=0.3），外加格式惩罚(-0.5)、长度惩罚、去重惩罚、core 特异性、归因加权。训练用 GRPO + 分层课程，不经过 SFT 热启动。
  • 查询端算法 (Read/Query): 每个会话用 DSL（TYPE:ACTION|field1|field2）一次性输出 4 个槽位全部记忆操作（单次模型调用替代 4 次）。推断/评测时：答案模型接收 Core 画像 + top-$k$ QA=10 检索记忆 + 可选的支撑对话块（由片段索引回溯到源轮次，提供 provenance）+ 当前时间上下文，生成回答，再由 LLM judge 打分。检索由记忆片段作索引到源对话，比压缩摘要更保真（MCC 类精确取数任务优势明显）。
  • 省Token标注: 有，量化明确：(1) 训练时 CMI+QA 策略的平均响应长度仅为 QA-only 的 39%，且内存库更小（635.6 条/420.3K 字符 vs 670.5 条/454.1K 字符；procedural 条目平均减少约 40%）；(2) 单次 DSL 响应一次输出四槽操作，减少 LLM 调用次数；(3) 一系列惩罚项（长度/重复/格式）直接压制冗余写入；(4) CMI 逐操作稠密信号带来更高效训练与更短 rollout。4B 小模型替代大模型记忆编排本身就是构建端省 token。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 最接近「构建端减 token + 提精度」的范式：用轻量管理器 + 内在信息论奖励驱动模型「少写、写有用的」，训练响应长度砍 61%、记忆库变小，同时精度还涨（CMI+QA 消融 67.0 vs QA-only 56.5；MemoryAgentBench 上 4B 超 MemBuilder-RL 11 个点）。CMI 奖励天然惩罚冗余写入，是「选择性存储」的可学习替代。「片段索引到源轮次」的查询端设计保证查询不受压缩损失，可与构建端压缩搭配达成「查询持平」。局限：精度提升主要在跨任务泛化（OOD），同类任务内提升相对温和。
  • 信息置信度: 高

Mem-α: Learning Memory Construction via Reinforcement Learning

  • Venue/Year: arXiv:2509.25911（2025 预印本；开源 wangyu-ustc/Mem-alpha）
  • 作者: Yu Wang, Ryuichi Takanobu, … , Xiaojian Wu
  • 类型: 系统构建（RL 训练框架 + 记忆架构）
  • 核心思想: 将记忆构建建模为序列决策 MDP，用 RL 训练 agent 自主决定「存什么、如何结构化、何时更新」，reward 直接来自下游 QA 准确率，替代预定义记忆指令。
  • 构建端算法 (Write/Build): 每处理一个输入 chunk $ct$，agent 观察当前记忆状态 $M{t-1}$（含 core/semantic/episodic 三层），执行最多 $Kt$ 个写操作，动作空间 $A{write}={memory_insert, memory_update, memory_delete}$，每个动作带参数（记忆类型、条目 id、内容）。Core memory 是常驻 prompt 的单一文本摘要（上限 512 token），只允许整体重写的 memory_update；semantic memory 是事实条目集合、episodic memory 是带时间戳事件账本，均支持 insert/update/delete。token 消耗点：每个 chunk 上的每次写操作都是一次 LLM 工具调用，构建端 LLM 调用次数与输入长度成正比，是构建/查询 token 失衡的主因。
  • 查询端算法 (Read/Query): 用「解耦 RAG 管线」评估记忆完备性：构建完成后对每个问题 $q_j$，固定检索器 $\varphi$ 用 BM25 分别对 semantic 与 episodic 记忆池取 top-$k$，冻结生成器 g 用检索支撑集生成答案并比对真值（$r_1$）。推理时 core 常驻上下文、检索到的条目注入 prompt。检索与生成均冻结不可学习——只有写策略可学习。总 reward 四部分：$r_1$ QA 正确性（冻结 RAG）、$r_2$ 工具调用语法有效性、$r_3$ 记忆压缩奖励、$r_4$ 语义有效性（LLM 评判）。
  • 省Token标注: 有。压缩奖励 $r_3$ 直接惩罚冗长记忆（$\beta$ 权衡，最优 $\beta=0.05$），训练 agent 写出精简记忆；core 硬性上限 512 token；训练仅用 ≤30k token 样本，外推到 400k+（13 倍以上）。未见查询端专门的 token 优化。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 压缩奖励是把「构建端省 token」融入目标函数的现成手段，但每次写操作仍是逐 chunk LLM 调用——需要更激进的「一次构建」（如压缩/latent 表示）而非逐条工具调用。查询端 BM25+冻结生成是低 token 的，可作「查询持平」参照系。

Mem-T: Densifying Rewards for Long-Horizon Memory Agents

  • Venue/Year: arXiv:2601.23014（2026 预印本；另见 ICML 2026 poster）
  • 作者: Yanwei Yue, Guibin Zhang, Boci Peng, Xuanbo Fan, Jiaxin Guo, Qiankun Li, Yan Zhang
  • 类型: 系统构建
  • 核心思想: 自主记忆 agent 对接轻量层次记忆数据库，提出 MoT-GRPO 把稀疏终端奖励转成稠密逐步监督，端到端联合优化记忆构建与检索（过程监督 + 归因）。
  • 构建端算法 (Write/Build): 层次库含 4 模块：Working Memory（每步更新精简摘要，保持片段内一致性）、Factual Memory（声明性知识）、Experiential Memory（程序性/经验知识）、Raw Memory（跨会话原始数据归档）。构造分两步：formation 策略 $\pi{form}$ 从输入流识别重要信息并选动作 $A{form}={CrtFact, CrtExp, CrtRaw, UpdWork}$；evolution 策略 $\pi_{evol}$ 决定如何整合进已有库（ADD/UPDATE/DELETE）。token 消耗点：每个 chunk 上的 formation+evolution 均为 LLM 策略调用。
  • 查询端算法 (Read/Query): 检索由 retrieval 策略 $\pi_{retr}$ 迭代式多轮自主搜索：不断从不同记忆模块选择搜索动作收集证据，直到模型自认为信息足够才生成最终答案 y。MoT-GRPO 对每个查询构建「记忆操作树」（Memory Operation Tree）探索多条检索路径，以记忆条目与证据为枢纽做节点级 reward 反向传播 + hindsight credit assignment，把推理反馈反传去评价对应构建操作质量；dual-track 同时训练构建与检索。
  • 省Token标注: 有，是主打卖点。相对 GAM 基线，推理 token/查询减少约 19.94%~24.45%，同时 F1 提升 5.17~28.48（最多超 A-Mem/Mem0 达 14.92%），位于 LoCoMo/HotpotQA 的 accuracy-efficiency Pareto 前沿。机制：稠密化奖励训练 agent 更精准——避免冗余搜索与无关记忆更新，即靠「减少 LLM 调用次数」而非压缩存储来省 token。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 证明「省 token 的主杠杆是减少不必要的 LLM 调用/冗余检索，而非压缩」；端到端 RL 让查询端也能省 20%+ token，说明查询端同样有优化空间，不必只盯着构建端；把 sparse 终端奖励变成稠密 step 奖励是让 agent 学会「少干活」的关键训练技术。
  • 信息置信度: 高

AtomMem: Building Simple and Effective Memory System for LLM Agents via Atomic Facts

  • Venue/Year: arXiv:2606.19847（2026-06 预印本；代码 github.com/MINE-USTC/AtomMem）
  • 作者: Yanyu Yao et al.（Shangze Li, Zhi Zheng, Hui-Wen Zheng, Qi Liu, Tong Xu, Enhong Chen；中科大）
  • 类型: 系统构建（原子事实记忆 + 分层事件 + 时间画像 + 图检索）
  • 核心思想: 把长对话压缩为「原子事实」（自包含、可独立检索的最小语义单元）作为记忆基元，再组织成层级事件结构与时间画像，查询时用关联记忆图把碎片化记忆串起来。强调「存储质量优先」：事实级扁平变体（AtomMem-Flat）仅用 722K token 就比原文历史的 LoCoMo 基线 F1 提升 76.6%。
  • 构建端算法 (Write/Build): 三条写路径，全部以 LLM 为驱动：(1) 原子事实抽取——SFT 微调的轻量抽取器（Qwen3-14B，LoRA rank 128，专用 4,352 样本数据集，GPT-4o 教师 + 人工精修）对每轮对话做去噪、指代消解、时间锚定，产出事实文本 + 结构化元数据 ${id, c, v, P, K, T, E}$（参与者/关键词/时间/事件id列表）；(2) 事实校验——存前先用参与者/时间做符号过滤缩小候选，再用混合相似度 $Sh = \alpha \cdot \text{语义} + \beta \cdot \text{关键词 Jaccard}$（α=0.7/β=0.3）取 top-$k$，LLM 判断新事实与已有事实关系，**只存「残余新信息」$c’{new}$，检测到冲突才生成更新 U——这是去重/防膨胀的关键；(3) 事件与画像——LLM 路由新事实入已有事件或建新事件（吸收时 LLM 重写摘要和关键词），画像用会话级批处理（抽取时把疑似长期属性入队，会话结束时批量用 LLM 更新，保留历史版本 H）。token 消耗点**：每轮事实抽取 LLM 调用、校验/去重 LLM 调用、事件吸收重写、会话末画像批处理。
  • 查询端算法 (Read/Query): 三级检索：(1) Query intent analysis——LLM 把查询 $q$ 解析为结构化对象 ${I_{prof}, P_q, K_q, T_q}$（是否需要画像/参与者/关键词/时间范围）；(2) Hierarchical Hybrid Retrieval——先做 Primary recall（按参与者和时间过滤后按 $S_h$ 取 top $k_s/2$ 个事实），再做 Compensatory recall（事件层按 $S_h$ 排序取 top 事件、融合分 $S_f = w_e \cdot S_h(E,Q) + (1-w_e) \cdot S_h(F,Q)$ 选 top $k_s/2$），合并为 seed 集；(3) Associative recall——以 seed 激活记忆图（实体边=IDF 加权关键词重叠、事件边=同事件、时间边=相邻轮次指数衰减），做带重启的随机游走/个性化 PageRank（重启概率 $\eta=0.34$，最多 2 跳、局部图≤180 节点），取 top $k_f=10$ 事实。若需要再检索画像（top $k_p=5$）。最终上下文 = 事实集 + 画像集 + 原查询喂给 LLM。全程仅 2 次主要 LLM 调用（意图解析 + 答案生成），检索管线本身仅 145.8ms、图重排 109.9ms。
  • 省Token标注: 有，量化明确。核心是「选择性压缩存储」：把冗杂对话压成高价值原子事实，总 token 相比 Mem0 降低约 61.4%（AtomMem 21,357K vs Mem0 55,300K）；扁平变体 AtomMem-Flat 用全方法最低的 722.75K token。手段包括：只存残余新信息（不存重复）、冲突才更新、画像会话级批处理（避免逐轮 LLM 重写）、检索容量 $k_f=10$ 封顶（超 20 会因噪声精度下降）。注意：完整版构建更精细，token 高于 LightMem(5,021K) 和 A-Mem(11,687K)；真正的「极省」版本是 AtomMem-Flat。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 最直接相关——「原子事实 + 只存增量/去重校验」是构建端压缩的可行范式，其扁平变体证明压缩存储本身就能同时大幅省 token 并提精度（Multi-Hop F1 20.97→37.03）。查询端 LLM 调用已压缩到约 2 次/问，查询 token 基本持平或更低。精度提升显著（LoCoMo 各任务 J-score 60-78）。完整版构建开销大、依赖专用 SFT 数据集；可借鉴「只存增量 + 批量画像」而砍掉多余 LLM 重写轮次。
  • 信息置信度: 高

SimpleMem: Efficient Lifelong Memory for LLM Agents

  • Venue/Year: arXiv:2601.02553（2026 v3；ICML 2026 Poster；GitHub: aiming-lab/SimpleMem）
  • 作者: Jiaqi Liu et al.（Yaofeng Su, Peng Xia, Siwei Han, Zeyu Zheng, Cihang Xie, Mingyu Ding, Huaxiu Yao）
  • 类型: 系统构建（基于「语义无损压缩」的高效终身记忆框架）
  • 核心思想: 以语义无损压缩为核心，把记忆当作主动过程而非被动存储：源头过滤低信息对话、写入时在线合并冗余、查询时按意图自适应定检索范围，使 Agent 在固定上下文/token 预算下回忆更多、花钱更少。
  • 构建端算法 (Write/Build): 三段流水线。Stage1 语义结构化压缩：把对话按滑动窗口 $W=20$ 轮、步长 5 切分；用基座 LLM 的指令跟随做「隐式语义密度门控」（$\Phi_{gate}$ 生成式过滤，输出空集即低密度闲聊窗口直接丢弃，无阈值调参）；随后一次联合生成完成提取+共指消解+绝对时间戳锚定（ISO-8601），产出上下文无关的紧凑记忆单元——每窗口约 1 次 LLM 调用（单遍处理）。单元用三视图索引：稠密向量（Qwen3-embedding-0.6b, 1024维, LanceDB IVF-PQ）+ BM25 稀疏 + SQL 符号元数据。Stage2 在线语义合成：写入阶段即时用 LLM 把相关碎片合并成统一高密度条目（如「喜欢咖啡/燕麦奶/喝热的」→「偏好热咖啡配燕麦奶」），消除冗余。案例：2.4 万原始 token 的跨会话历史压缩到约 800 token。
  • 查询端算法 (Read/Query): Stage3 意图感知检索规划：每查询先由 LLM 推理出检索计划 ${q{sem}, q{lex}, q_{sym}, d}$，$d$ 为自适应检索深度，候选数 $n \propto d$，范围 $k \in [3,20]$；并行对三视图检索（稠密余弦 Top-n、BM25 Top-n、符号过滤 Top-n），结果做集合并集天然去重，直接构造上下文，重排关闭。之后基座 LLM 生成答案。每查询 LLM 调用约 2 次（检索规划 + 答案生成）。
  • 省Token标注: 省 token 是核心卖点，量化充分：(a) 查询推理 token 减约 30×——full-context 基线约 16,900 token/查询，SimpleMem 平均仅 531–583 token/查询；比优化检索基线 Mem0(~980)/A-Mem(~1200+) 再少 40–50%；(b) 构建端单遍处理 92.6s/样本，比 Mem0(1350.9s, 14×) 和 A-Mem(5140.5s, 50×) 大幅更快（构建 LLM 调用数远低于 Mem0 图更新/A-Mem 迭代摘要）；(c) 写入端在线合成把去重前移到写阶段，避免查询时碎片拼装；(d) 自适应检索「深查询才多取」控制预算。精度同步提升：LoCoMo 平均 F1 43.24（GPT-4.1-mini），较 Mem0 34.20 提升 26.4%（Temporal 58.62 vs 48.91）；LongMemEval-S 平均准确率 76.87% vs Mem0 59.81%。消融：去语义压缩 → Temporal F1 −56.7%；去在线合成 → Multi-hop −31.3%；去意图检索 → Open-domain −26.6%、Single-hop −19.4%。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 几乎直接命中项目目标：用「单遍联合抽取（门控+共指+时间锚定）+ 写入端在线合成」把构建成本降到同类 1/14~1/50（远超减 50% 目标），用「意图感知检索规划 + 三视图并行检索 + 关闭重排」把查询 token 减 30× 且与精度同升（F1 +26.4%）。最值得借鉴：门控式生成过滤（空集即丢弃）、在写入阶段而非查询阶段去冗余、检索预算由查询复杂度自适应而不是固定 top-k。
  • 信息置信度: 高

What Deserves Memory: Adaptive Memory Distillation for LLM Agents（NEMORI）

  • Venue/Year: ACL 2026 (Long Papers)（arXiv:2508.03341；开源 nemori-ai/nemori）
  • 作者: Wenquan Ma, Jiayan Nan, Wenlong Wu, Yize Chen
  • 类型: 系统构建 / 框架（training-free 蒸馏层，可接任何下游记忆系统）
  • 核心思想: 受预测编码理论与互补学习系统启发，把「经历未来是否有用」重定义为其可预测性——现有知识预测不了的经历才值得留存为记忆；两个级联模块做蒸馏，放弃启发式重要性打分。
  • 构建端算法 (Write/Build): 三模块级联：(1) 主题分割（LLM 边界检测 + 过渡掩蔽启发式，把对话切成语义连贯片段）；(2) Episodic Memory Integration：每段转成带时间锚点与来源的连贯叙事；(3) Semantic Knowledge Distillation 三步：Predict 用已有语义知识预测新情节内容 $\hat{e}$ → Calibrate 把 $\hat{e}$ 与原始未处理对话块 M（ground truth）对比，LLM 蒸馏器 $r\omega$ 识别「预测缺口」，蒸馏出新的语义知识陈述 $K{new}$ → Integration 并入语义知识库。token 消耗点：分割、情节生成、预测、校准蒸馏共约 4 类 LLM 调用，但产出物（叙事+语义陈述）远小于原文，属于「用一次 LLM 调用换长期低 token 存储」。
  • 查询端算法 (Read/Query): 统一向量检索 $Retrieve(q, D, m, \sigma_s)$：dense vector + cosine 相似度，三阶段（相似度计算 → 候选选择 → 阈值过滤），对 episodic 与 semantic 两库统一访问。生成回答时同时使用情节库与语义库。蒸馏过程中也会检索相关语义记忆（以新情节的 title⊕content 嵌入为查询）。
  • 省Token标注: 有。episode-centric 设计：以「叙事+语义陈述」替代原始日志，即蒸馏即存储。LoCoMo 上平均 2,745 token/查询 vs FullContext 23,653（减少约 88%），且精度更高（gpt-4o-mini: LLM Score 0.744 / F1 0.495 / BLEU-1 0.385；gpt-4.1-mini: 0.794 / 0.534 / 0.456）。预测误差式蒸馏 vs 直接蒸馏：gpt-4o-mini 65.0 vs 52.0（+25%），gpt-4.1-mini 74.9 vs 65.5（+14.4%）。框架 training-free（无 RL/微调）。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 「蒸馏即存储 + 统一向量检索」同时压缩了构建端产物和查询端 token（88% 削减是「查询端更省」的现成实证）；用数据驱动的预测误差替代启发式重要性，是提升记忆精度（F1/BLEU）而非依赖更多 token 的可行方向——直接对应「查询持平但精度+20%」的目标路径。
  • 信息置信度: 高

Rethinking How to Remember: Beyond Atomic Facts in Lifelong LLM Agent Memory（TriMem）

  • Venue/Year: arXiv:2605.19952（2026 预印本；项目页 TMLR-TriMem.github.io）
  • 作者: Jingwei Sun et al.
  • 类型: 系统构建 + 实证研究（三粒度记忆架构，名为 TriMem）
  • 核心思想: 现有 Agent 记忆普遍是「事实抽取」范式——静态 prompt 把对话压成原子事实再存/匹配/注入，但会丢弃细粒度细节、难以支撑跨孤立事实的深层推理，且静态 prompt 无法在不同对话风格下保持一致的抽取粒度。TriMem 主张同时维护三种粒度：原始对话片段（保真）、抽取的原子事实（高效检索）、合成的用户画像 profile（深度推理）。
  • 构建端算法 (Write/Build): 三级管线：原始对话 → 抽取关键事实 → 集成 profile。①原始对话按片段留存，并为每条压缩记忆建「源对话标识符」索引（traceable link），指针指向原始对话片段，解决保真问题；②事实抽取用 prompt 从对话抽原子事实；③profile 模块在摄入时增量整合散落的事实，形成整体性理解。提示词优化用 TextGrad 做基于响应质量反馈的迭代精化（实验中失败案例分析由 Claude Opus 4.6 完成）。token 消耗点：事实抽取 prompt、profile 增量整合 prompt、TextGrad 反馈优化循环（构建端额外花 token）。
  • 查询端算法 (Read/Query): 用原子事实做高效检索匹配，命中后经 traceable link 回溯原始对话片段获取细节，并召回相关 profile 支撑理解式/多跳推理。论文报告平均检索上下文约 1.2k tokens——「检索原始对话+实体 profile 略微增加 token 开销，但换来明显性能提升」。
  • 省Token标注: 有。事实+profile 的压缩表示让查询上下文压到 ~1.2k tokens（相对全量对话大幅压缩）；profile 增量整合避免重复存储同一用户信息。代价是构建端多一层 TextGrad 优化与 profile 整合；论文明确承认检索端「略微增加 token 开销」以换取精度。LoCoMo 上（多 backbone，含 GPT-4o/GPT-4.1-mini/GPT-5-nano）持续优于强基线，另在 PerLTQA 验证泛化。

  • 作者: Ningning Zhang et al.

AtomMem: Learnable Dynamic Agentic Memory with Atomic Memory Operation

  • Venue/Year: arXiv:2601.08323（2026-01 预印本 v3；代码 github.com/RUCBM/AtomMem）
  • 作者: Yupeng Huo et al.（Yaxi Lu, Zhong Zhang, Haotian Chen, Yankai Lin；人大 + 清华）
  • 类型: 系统构建（可学习记忆策略；POMDP + RL）
  • 核心思想: 把 agent 记忆管理重新建模为 POMDP 决策问题，将高层记忆流程拆解为原子 CRUD（Create/Read/Update/Delete）操作，用强化学习（GRPO）让模型自主学会按任务决定何时「写/读/改/删」，取代人工写死的静态记忆流程。注意与 USTC 的同名论文不同（本文是 CRUD+RL 方向）。
  • 构建端算法 (Write/Build): 长文本被切分为 4k-token 块逐块喂入；模型在每一步输出结构化 XML 记忆动作。Create 用 <create_memory>{content}</create_memory> 写入 FAISS 向量库；Update 用 <update_memory>{id: content}</update_memory> 按 ID 局部改写；Delete 用 <delete_memory>id</delete_memory> 永久删除。非 Read 动作按序复合执行，构成宏动作。token 消耗点：模型生成记忆内容本身的输出 token + 注入上下文的历史/检索内容。RL 训练（GRPO，Qwen3-8B）用任务级成功作唯一奖励（QA 用 EM，web 任务用 LLM-judge）；训练约 8 卡 A800 跑 2-3 天。
  • 查询端算法 (Read/Query): 混合检索，分两路：(1) Deterministic retrieval——特殊记忆条目 $m_{scr}$（scratchpad）每步无条件注入，保存全局任务状态与关键信息；(2) Selective retrieval——模型主动生成文本查询 $q_t$ 作为 Read 动作参数（<read_memory>{query}</read_memory>），按语义相似度 TopK 检索（默认 top-6）。观测 = 环境观测 + scratchpad + 检索集。是否 Read 是学出来的策略（RL 后 Read 频率大幅下降并稳定在低位，Create/Update/Delete 上升，即模型学会「少查多写、紧凑存储」）。

  • 对目标(构建减50%/查询持平/精度+20%)的启示: (1) 证明「写什么/写不写」可经 RL 学成策略，天然减少无谓写入与冗余检索；(2) 冗余检索（Read 过多）是主要浪费，压缩 Read 频率是省查询 token 的有效杠杆；(3) Update/Delete 等「改写式写入」对精度贡献大（消融掉 Update 平均降 ~6 分），提示构建端做增量改写而非全部重写可兼顾省 token 与精度。但本身不专门优化构建 token，需叠加压缩手段才可能达成「构建减 50%」。

A-Mem: Agentic Memory for LLM Agents

  • Venue/Year: NeurIPS 2025（arXiv:2502.12110）
  • 作者: Wujiang Xu et al.（Wujiang Xu, Zujie Liang, Kai Mei, Hang Gao, Juntao Tan, Yongfeng Zhang）
  • 类型: 系统构建
  • 核心思想: 基于 Zettelkasten（卡片盒笔记法）构建互联的知识网络；每次新记忆写入时都做「建卡-建链-演化」三步，由 LLM 动态组织记忆，而非只在查询端优化。
  • 构建端算法 (Write/Build): 每次交互写入一条记忆笔记 $mi = {c_i, t_i, K_i, G_i, X_i, e_i, L_i}$（内容/时间戳/关键词/标签/上下文描述/嵌入/链接）。写入时 3 类 LLM 操作（附录有 Note Construction / Link Generation / Memory Evolution 三个独立 prompt）：(1) 建卡——用模板 $P{s1}$ 让 LLM 生成关键词、标签、上下文描述；(2) 建链——对新笔记先做嵌入余弦相似度检索出 top-k 候选旧笔记，再由 LLM 判定哪些建立语义链接；(3) 演化——新记忆整合后触发 LLM 重写既有相关笔记的上下文描述与属性。token 消耗点：每次写入 ≥3 次 LLM 调用（属性生成 + 链接判定 + 既有笔记更新），构建侧明显偏重。
  • 查询端算法 (Read/Query): 给定当前查询 $q$，用与笔记相同的文本编码器计算稠密向量 $e_q$，与所有笔记做余弦相似度排序（纯向量运算，检索环节无 LLM 调用），top-k 相关笔记拼入 agent 上下文。查询端 LLM 调用点：仅最终的回答生成。

  • 对目标(构建减50%/查询持平/精度+20%)的启示: 反面教材——「写时做重活（多 LLM 调用生成属性+建链+演化）」与「构建 token 减 50%」目标直接冲突。但其查询端证明「纯相似度检索、检索环节零 LLM 调用」可让查询开销很低；结构化链接换来了 multi-hop 精度大幅提升。

HeLa-Mem: Hebbian Learning and Associative Memory for LLM Agents

  • Venue/Year: ACL 2026（arXiv:2604.16839）
  • 作者: Jinchang Zhu et al.
  • 类型: 系统构建（仿神经科学的图式关联记忆架构）
  • 核心思想: 把记忆建模为带 Hebbian 学习动力学的动态图：共激活的记忆反复出现会不断强化彼此连接（associating），密集连接的枢纽（hub）由「反思智能体」蒸馏成稳定的语义知识（consolidation），查询时通过扩散激活检索（spreading activation）。
  • 构建端算法 (Write/Build): 两级存储。①情景记忆图：每一对话轮作为一个带权图节点，节点存原始文本、稠密 embedding、时间戳、抽取的关键词、说话者角色；边表示关联强度，初始时相邻轮连小权重边，随后经 Hebbian 学习按共激活动态加强（权重演进，非 LLM 调用，是向量/相似度运算）。②语义记忆库：当关联强度超过阈值，反思智能体找出枢纽节点簇，对其施加 Hebbian 蒸馏——用专门 prompt 让 LLM 从记忆簇抽取结构化知识（用户特征需带证据、事实信息含时间地点/偏好/关系），产出精炼的语义记录，且保留可追溯的证据链接回源轮次，防止图爆炸与噪声累积。构建端 LLM 调用点：主要是蒸馏时的一次 prompt（反思智能体），以及对每轮关键词的抽取；Hebbian 权重更新本身无 LLM 开销。
  • 查询端算法 (Read/Query): 双路检索 + 扩散激活。查询同时激活「具体情景细节」与「更广的语义知识」：先按语义相似度得到种子节点，再沿 Hebbian 边扩散激活，最终得分 = 语义相似度 + Hebbian 贡献。论文给出实例：$S_{total} = 0.35(\text{语义}) + 0.36(\text{Hebbian}) \approx 0.71$，从而找回相似度低(0.35)但关联强的旧轮次，突破「语义陷阱」。无 LLM 打分/重写，主要算力在向量与图遍历。
  • 省Token标注: 有，量化。LoCoMo 上上下文 token 仅 1,010（对比：全量 16,910、MemGPT 16,977、A-Mem 2,520、MemoryOS 2,000、ReadAgent 643、MemoryBank 432）。相比全量/MemGPT 减 94%，是四篇里省 token 最激进的（检索端）。同时四类问题 F1/BLEU-1 全部最优（如 Single Hop F1 51.89、Temporal F1 47.29），四类平均 rank 1.25。代价是构建端仍要逐轮存原始文本 + 蒸馏 LLM 调用。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 证明「关联/蒸馏式记忆」能在查询端把 token 压到全量的 ~6% 同时精度反超——但 token 节约在查询端（注入上下文变少），构建端反而更重（存原始文本+蒸馏）。「把高频共激活记忆在线蒸馏成精炼语义记录（带证据链接）」是可直接借鉴的构建端压缩手段；Hebbian 边的图检索是低成本（非 LLM）提精度路径。
  • 信息置信度: 高

  • 核心思想: 记忆不是「被动检索」而是「主动重建」——把 LLM 推理直接并入记忆访问，在 Cue–Tag–Content 关联图上迭代探索/剪枝检索路径，用中间证据动态调整下一步；理论证明主动（有状态）检索策略严格强于被动检索。在 LoCoMo 上相对最强基线 LLM-Judge 提升最高 23%，同时显著降 token 与耗时。

  • 查询端算法 (Read/Query): 主动重建循环：query 抽 cue→匹配存储 cue 得初始活跃集→迭代 { LLM 动作选择 $f{select}$（基于 query+已积累证据+活跃集选遍历动作）→ 受控遍历（7 个工具算子：query_tag_events、query_conversation_time、query_event_keywords、query_event_context、query_personal_information、query_personal_aspect、query_topic_events）→ LLM 路由/剪枝 $f{route}$（评估新候选与 query/上下文的语义关联，剪掉无关分支）→ 充分性判定 Stop }。执行模式 Navigate→Answer；预算上限每 query 最多 8 轮推理、每轮最多 10 次工具调用。tag 作为廉价中间层：先在 tag 层选路、剪枝，再访问昂贵的完整情节内容。
  • 省Token标注: 有，是全文核心卖点：① 写侧轻量化——把关系建模从构建推迟到检索（on-demand），构建阶段 token 极省；② tag 中介剪枝——访问内容前先用关联 tag 选路，避免组合爆炸；③ 选择性检索 + LLM 早停（Max Valid Turns≈Average Turns，冗余探索少）；④ 预算硬上限（8 轮×10 工具）。量化：token 118k vs 最强基线 Mem0 245k（约 -52%）、vs A-Mem 632k（-81%）；runtime 与 Mem0 持平。精度：LoCoMo Gemini 下 overall J 68.31→84.21（+23.3%），Claude 下 +12.4%；LongMemEval overall J 72.95 vs 最强基线 54.92（+32% 相对）。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 与目标高度吻合的现成方案：构建 token 大幅削减（轻量蒸馏+推迟关系建模，远超 -50%），精度提升远超 +20%。但「查询持平」有风险——多轮重建每步都是 LLM 调用，token 持平靠预算硬帽（8 轮/10 工具）与 tag 剪枝实现。可作为主候选：写侧极简抽取、查侧按需重建，代价是查询端 LLM 调用次数增加，需进一步做「查询端预算控制」来真正压到与单发检索持平。

  • 作者: Yushi Sun et al.（Yushi Sun, B. Cao, D. Fang, L. Su, W. Lam）
  • 类型: 系统构建（可插拔结构化记忆模块，外部增强而非自建完整 Agent 记忆系统）

  • Venue/Year: arXiv:2605.04897（2026 技术报告；github.com/buildingjoshbetter/TrueMemory）
  • 作者: Joshua Adler, Guy Zehavi
  • 类型: 系统构建
  • 核心思想: 核心论点：「ingestion 时的抽取是错误原语——在查询未知前丢弃的内容，检索时无法找回」。提出 True Memory：六层(L0–L5)架构，重心从存储 schema 转向多阶段检索流水线，事件逐字(verbatim)保留，理解性结构后置计算。整套系统跑在单个 SQLite 文件的普通 CPU 上，无外部数据库/向量索引/图存储/GPU。

  • 作者: B. Yan et al.（Chaofan Li, Hongjin Qian, Shuqi Lu, Zheng Liu）
  • 类型: 系统构建
  • 核心思想: 提出 GAM 框架，遵循「just-in-time (JIT) 编译」原则——离线阶段只保留简单有用的轻量记忆，完整历史无损存入 page-store；在线阶段用 agentic 深度研究按需构建优化上下文，避免静态记忆预先压缩导致的信息丢失。

  • 对目标(构建减50%/查询持平/精度+20%)的启示: 构建减 50% 可直接借鉴「轻量摘要 + 小模型 Memorizer + 无损存储」；查询持平需配合预算控制（限反思深度=3、限页数=5）。精度提升证据强：LoCoMo（GPT-4o-mini 骨干）Single-Hop F1 57.75 / Multi-Hop 42.29 / Temporal 59.45 / Open-Domain 33.30，RULER 多跳追踪准确率 93.20，NarrativeQA F1 36.86，全面超过 long-LLM、RAG、A-Mem、Mem0、MemoryOS、LightMem。但查询端 token 会显著上升，直接照搬会违背「查询持平」约束。

  • 对目标(构建减50%/查询持平/精度+20%)的启示: 分层摘要 + 两阶段检索（先段级粗筛再页级细筛）是「构建端压缩、查询端可控」的成熟模板，可在查询端显著控 token；精度证据强——LoCoMo 上相对基线平均 F1 +49.11%、BLEU-1 +46.18%（gpt-4o-mini 骨干），GVD 上较 A-Mem 准确率 +3.2%。但构建端 LLM 摘要成本需另做压缩（如用小模型/抽帧），否则减 50% 目标不易达标。

  • 信息置信度: 高

  • 问题: 他在STM时期就算语义信息可以被看作连贯，却还是通过LLM判断为无关，产生了冗余的大模型总结开销。 (图为一个测试样例)

MemOS: A Memory OS for AI System

  • Venue/Year: arXiv:2507.03724（2025 v4；上海 AI Lab/复旦系）
  • 作者: Zhiyu Li et al.（约 40 位作者）
  • 类型: 系统构建
  • 核心思想: 把「记忆」当作与算力同等的一等系统资源。提出统一抽象 MemCube（封装记忆内容+元数据：来源 provenance、版本 versioning），统一明文记忆(plaintext)、激活记忆(activation)、参数记忆(parameter)三种形态，用调度器做选择、预加载、过滤，让记忆像 OS 资源一样被调度、进化。
  • 构建端算法 (Write/Build): 明文记忆被封进可调参的 MemCube（含生命周期控制、访问策略、版本追踪）；明文记忆按「任务–概念–事实」路径组织成层级图结构存储；支持记忆的插入、融合、重构，随时间演化（compose/migrate/fuse）。高频明文记忆可被转换为激活路径（外部知识「内化」为激活记忆），实现知识的外化/内化动态切换。构建发生在记忆创建/更新时，涉及 LLM 调用。
  • 查询端算法 (Read/Query): Memory Scheduler 类似 OS 调度器，按任务动态管理参数/激活/明文三种记忆——选择、预加载、优化过滤最相关的片段；Next-Scene Prediction（下一场景预测） 机制在推理中主动预加载相关记忆片段；MemCube 支持基于查询的聚合与多粒度激活；用上下文指纹、时间戳加载做精确取用；图结构语义交叉链接支撑灵活推理。
  • 省Token标注: 有，量化最强。LoCoMo 上：较 OpenAI 全局记忆，时序推理提升 159%，整体准确率提升 +38.97%，token 开销降低 60.95%。手段：(1) Next-Scene Prediction 预加载避免重复/冗余注入；(2) 调度器只加载相关片段（选择性加载）；(3) 激活记忆直接注入 KV/注意力，不占输入 token；(4) 明文↔激活转换实现外化/内化。前提：激活/参数记忆需要对模型内部有控制权（开源权重模型），闭源 API 下只剩明文层。TTFT 加速表：short/medium/long 场景 KV TTFT 相对 baseline 提速 23%~94%。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 四篇中最贴合目标的一篇——同一系统内同时达成「token 减 60.95% + 精度大幅提升」，构建/查询双侧都省。可借鉴：主动预加载（省查询 token）、按需调度选择性注入、把高频知识下沉到更省 token 的表示层。局限：依赖可改模型内部的开源栈，对纯 API agent 只可复制明文层部分。数字为论文方自报，未见第三方复现。
  • 信息置信度: 高

MemoryBank: Enhancing Large Language Models with Long-Term Memory

  • Venue/Year: AAAI 2024（arXiv:2305.10250）
  • 作者: Wanjun Zhong et al.
  • 类型: 系统构建（含实证，构建了 AI 陪伴机器人 SiliconFriend）
  • 核心思想: 三支柱式记忆机制——存储（对话记录/事件摘要/用户画像）、检索（DPR 式双塔稠密检索）、更新（受 Ebbinghaus 遗忘曲线启发的人类式遗忘与强化），使 LLM 在长期陪伴场景中可回忆、可演进、可理解用户人格。
  • 构建端算法 (Write/Build): 存储层分层保存：日常对话记录、过去事件摘要、逐步演进的用户人格画像。事件摘要与用户画像由 LLM 对历史交互「综合信息」生成/更新（摘要替代旧的、画像持续刷新）。记忆更新用 Ebbinghaus 遗忘曲线控制留存：$R = e^{-t/S}$（$R$ 留存率，$t$ 距上次回忆的时间，$S$ 记忆强度）；$S$ 被离散化建模，首次提及时初始化，回忆一次 $S$ 增加 1 且 $t$ 重置为 0，降低遗忘概率；长期未回忆的低重要性记忆被选择性遗忘/删除。token 消耗点：LLM 摘要生成与画像更新调用；但遗忘机制使记忆库规模有界（不会无限增长）。
  • 查询端算法 (Read/Query): 把每轮对话与事件摘要视为「记忆片段」，预先用编码器编码为向量并用 FAISS 建索引；当前对话上下文编码为查询向量，检索最相关的记忆片段拼入上下文。检索环节为纯向量检索（双塔 DPR 式），无检索 LLM 调用。
  • 省Token标注: 有但未量化。手段：(1) 事件摘要（LLM 压缩对话记录）降存储体量；(2) 遗忘曲线作为存储预算控制器——低价值久远记忆被删，抑制记忆库膨胀；(3) 查询端 FAISS 向量检索，检索无 LLM 调用。在 Mem0 的 LOCOMO 评测中 MemoryBank 各指标明显偏弱（单跳 F1≈5.0 等），因其面向陪伴场景而非问答基准。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 「遗忘/选择性留存」是构建端 token 控制的天然手段（存储有界），摘要压缩同理；查询端零 LLM 调用、仅向量检索，可直接支撑「查询持平」。但精度（F1/BLEU）在问答基准上不达标，其价值更多在构建端规模约束。
  • 信息置信度: 高

Retain or Consolidate? Budget-Dependent Operator Selection for Language Agent Memory

  • Venue/Year: arXiv:2607.17545（2026-07 v2 预印本）
  • 作者: Qingcan Kang et al.
  • 类型: 实证研究 + 机制框架（记忆管理算子选择，非完整记忆系统）
  • 核心思想: 回答「何时该用 consolidation 替代 retention，以及该选哪个算子（Merge/Abstract/Rewrite）」。把每个 consolidation 算子的效用分解为覆盖效应（对被 retention 遗漏证据的增量覆盖）与带符号的替换效应（对已能容纳的原始证据，替换带来的损失），两者平衡决定「偏好动作随相对预算压力变化」——预算紧用合并，预算松保留原文。并用轻量学习器 OAS 落地。
  • 构建端算法 (Write/Build): 本文的「写/整理」即预算约束下的记忆表示生成（generative operators）：Merge 把多条笔记合并为一条紧凑事实记录；Abstract 跨输入合成更高层的摘要；Rewrite 对每条笔记独立改写后按预算打包（保留内部笔记边界）。每个生成算子输出被硬性封顶到目标预算 token（LongMemEval 上用 32/64/128/256 token 预算），属于「预算目标化表示」。OAS（Offline Abstraction-Safety）是轻量多动作效用学习器：用生成前的特征（预算规模、证据适配压力、聚类几何、查询类型）估计各动作（Retain/Merge/Abstract/Rewrite）效用，再用 plug-in 最大化选择；用留出集做安全校准阈值限制有害替换；主估计器为线性回归（监督数据少，适合低容量模型）。
  • 查询端算法 (Read/Query): 在预算内准备「给答案模型看的记忆」时执行选择：retention 保留原始记录（保真但紧预算下覆盖不足），consolidation 用生成算子压缩合并（每 token 覆盖更高但可能丢查询关键细节）。OAS 在生成前预测各动作效用后执行选择——属于查询/读时的记忆策展。
  • 省Token标注: 有，是核心。预算控制是显式设计：所有 consolidation 输出按目标预算 token 硬封顶（32/64/128/256）；consolidation 提升每 token 覆盖度，预算紧时尤甚。结果：LongMemEval 预算紧时 consolidation 相对 retention 绝对精度最高提升 48%；预算松时 retention 全面领先 consolidation 8~11%。LoCoMo 极紧预算下 Abstract/Merge 达 48.0%，retention 仅 12.9%、Rewrite 仅 26.7%；预算约 64 token 时交叉点出现。跨笔记 Abstract/Merge 通常优于局部 Rewrite。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 直接给出「token-精度」的预算条件性决策机制——预算紧合并、预算松保留，说明省 token 与精度可兼得的关键是按相对预算压力动态选择算子，而非统一策略；其「每 token 覆盖度」与「替换效应」的效用分解可作为设计高效记忆检索时的代价函数蓝本。OAS 用离线轻量模型估计效用（而非在线多调 LLM）本身就是省 token 手段。
  • 信息置信度: 高

Choosing How to Remember: Adaptive Memory Structures for LLM Agents（FluxMem）

  • Venue/Year: arXiv:2602.14038（2026 预印本）
  • 作者: Mingfei Lu et al.
  • 类型: 系统构建（自适应记忆结构框架，名为 FluxMem）
  • 核心思想: 现有 Agent 记忆系统把「记忆结构」当作固定设计选择，而非随交互内容自适应调整。FluxMem 提出在中期记忆中并行维护多种互补记忆结构（线性/图/层级），由一个轻量选择器按对话上下文动态选最合适的结构，并用 Beta 混合模型（BMM）门控做分布感知的融合。
  • 构建端算法 (Write/Build): 三层记忆层级，写入是逐级流转的管线：新生成的对话页先写入短期交互记忆 STIM（缓冲最近页面）→ 组织成中期情景记忆 MTEM（每个记忆单元是一段由多个语义/时间相关页面构成的情景会话）→ 再经合并算子 $\varphi_L$ 固化到长期语义记忆 LTSM（从历史交互抽象出的持久知识）。三种结构（线性/图/层级）沿用已有记忆方法实现。结构选择器是两层 MLP（输入 12 维、隐层 4），每个交互回合跑一次，输入是简单可解释的「结构信号」特征（而非深层语义向量）。token 消耗点：LTSM 的语义合并/固化、实体关系抽取，以及每回合一次的结构选择。论文明确指出开销主要来自结构选择与融合，骨干 LLM 推理本身不变。
  • 查询端算法 (Read/Query): 查询时跨三层记忆做检索→融合→生成：最终回复以 query 和检索到的记忆为条件。多结构检索后由 BMM 概率门做分布感知融合，取代脆弱的相似度阈值（门控同时控制记忆融合与更新）。无 LLM 重写/多轮打分，选择器是确定性 MLP 分类。
  • 省Token标注: 有间接的省 token 设计：(1) 选择器为 MLP（常数时间、可忽略开销），不引入 LLM 控制层推理，避免额外 token；(2)「更自适应、更选择性的记忆利用」意味着避免把所有记忆都塞进上下文。无压缩/蒸馏量化数字。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 用「可学习的结构选择（MLP + 离线监督）」替代每次 LLM 决策，是把「记忆组织」决策从 LLM token 里挪到廉价模型的做法——正是构建/查询两端省 token 的思路。PERSONAMEM 上平均精度 +9.18%（72.43%），LoCoMo 上 F1/BLEU-1/ROUGE-L 全面最优（+6.14%），证明「结构自适应」本身能显著提精度而几乎不增加 token。但未做构建端压缩，对「构建减 50%」的直接贡献有限。
  • 信息置信度: 高

MemPrivacy: Privacy-Preserving Personalized Memory Management for Edge-Cloud Agents

  • Venue/Year: arXiv:2605.09530（2026 预印本）
  • 作者: Yining Chen et al.（Jihao Zhao, Bo Tang, Hongya Wang, Yue Zhang, Fei Huang, Feiyu Xiong, Zhiyu Li）
  • 类型: 系统构建（隐私保护框架 + 数据集 + 专用模型训练）
  • 核心思想: 针对边缘-云端 Agent 的长时个性化记忆，MemPrivacy 在设备端把隐私敏感片段识别出来、替换成语义化类型占位符（如 <EMAIL_1>）再上传云端做记忆处理，需要时在本地还原原值，从而在不破坏任务相关语义的前提下把隐私暴露最小化。
  • 构建端算法 (Write/Build): 三段闭环。（1）上行脱敏：轻量端上模型（MemPrivacy-0.6B/1.7B/4B，Qwen3 底座，SFT 26K 条 + GRPO RL 1K 条，奖励=抽取 F1）识别输入中的隐私 span，产出 {原文、隐私级别 PL1–PL4、隐私类型} 结构，并按类型替换为语义占位符、同类型递增编号；原值与占位符映射存本地数据库，支持跨会话一致还原。（2）云端处理：占位符保留类型语义，云端 LLM 仍可做理解/推理/记忆写入，泄露只暴露占位符。（3）下行还原：本地查库+字符串替换，开销可忽略。token 消耗点：端上隐私模型一次抽取生成；云端记忆写入照常（内容是占位符版，比原文更短）。
  • 查询端算法 (Read/Query): 云端记忆系统（LangMem / Mem0 / Memobase，统一 GPT-4.1 后端）正常做检索与生成；检索时记忆里存的是占位符；云端响应含占位符时本地还原给用户。无额外 LLM 调用。
  • 省Token标注: 主要目标是隐私而非省 token，但有间接效率设计：(a) 专用小模型（0.6B–4B）抽取隐私，端上延迟 <1s，比 Gemini-3.1-Pro 等推理模型快 1–2 个数量级（Gemini 32.87s）；(b) 占位符通常短于原私密值（邮箱/地址/凭证等），云端记忆 token 数会相应变少（原文未量化，中置信度推断）；(c) 还原只做查库替换，不产生 LLM 调用。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 「端上小模型 + 类型化占位符」把敏感信息压缩为语义占位符的管道可移植到记忆构建端做轻量预处理；其 4B 小模型 F1(85.97) 大幅超越通用大模型（GPT-5.2 68.99 / Gemini-3.1-Pro 78.41），说明「用专门小模型替代大模型 LLM 调用」是同时降 token 和提精度的可行路线；多记忆系统上效用损失仅 0.71%–1.60%，证明该类改造不会牺牲 QA 精度。
  • 信息置信度: 高

Remembering More, Risking More: Longitudinal Safety Risks in Memory-Equipped LLM Agents

  • Venue/Year: arXiv:2605.17830（2026 预印本）
  • 作者: Ahmad S. Al-Tawaha et al.（Shangding Gu, Peizhi Niu, Ruoxi Jia, Ming Jin）
  • 类型: 安全分析（实证研究，非系统构建）
  • 核心思想: 指出记忆 Agent 的安全评测多只看「单任务内安全」，而部署中 Agent 长期服务多个独立任务，早前任务累积的记忆会污染后续无关任务的行为——称此失效模式为「时序记忆污染（temporal memory contamination）」；随暴露长度增加，记忆诱发违规率持续上升。
  • 构建端算法 (Write/Build): 不设计构建算法，但实验覆盖 8 种记忆架构（Full Memory, Short-Term, Long-Term, Generative Agents, MemoryBank, Self-Controlled Memory, MemGPT, MemTree）。相关机制发现：a) 摘要式构建（GA、SC 等频繁对记忆做抽象/合并）会「把多个独立上下文的细节合并成任何单条原始信息里都没有的新表述」，引入污染；b) 记忆体量增长稀释注意力（attention dilution）+ 例行开发交互使凭据类语言「正常化」。
  • 查询端算法 (Read/Query): 提出 trigger-probe 协议：固定探针集对 read-only 记忆快照评估；以 NullMemory（不检索任何上下文的对照基线）配对运行，判定「记忆诱发违规」需同时满足：记忆运行不安全 + NullMemory 运行安全 + 不安全内容可溯因到检索记忆（约 91% 的 judge-人工一致率）。另提出检索时风险监控器（Event-Structure 预测器）：只依据 (trigger, 检索上下文, 检索遥测) 在生成前预测违规，可触发检索过滤/无记忆生成/转人工验证。
  • 省Token标注: 无省 token 设计（安全分析）。但给出与「省 token」直接相关的警告：宽检索范围+强摘要合并会同时放大效用与安全风险；检索范围越广、摘要层越多，随记忆增长风险上升越快。监控器本身是轻量的（不跑生成即可预测风险），高召回（0.970/0.984）。
  • 对目标(构建减50%/查询持平/精度+20%)的启示: 对「压缩/蒸馏」路线提出安全约束：构建端摘要合并会引入原文不存在的具体性，因此设计蒸馏/合并记忆时需保留溯源（source trace）以防合并污染；「查询持平」目标下，若压缩不当反而会提高误答风险。检索时监控（生成前预测、高风险时跳过生成/降级检索）可作为低成本保险丝，且能顺带省掉不安全生成所耗 token。
  • 信息置信度: 高
